# Архитектурные решения (ADR)

Формат: **проблема → решение → последствия**. Все записи обязательны к прочтению
перед изменением соответствующего слоя.

## ADR-001. Не подключаем `telegram-web-app.js` с CDN

**Проблема.** Классическая интеграция требует `<script src="https://telegram.org/js/telegram-web-app.js">`,
это блокирующий сторонний запрос на критическом пути первого рендера (< 2.5 с) и
лишняя точка отказа (в WebView с плохой сетью скрипт может не загрузиться).

**Решение.** `@telegram-apps/sdk` v3 читает launch params из URL-хэша
(`tgWebAppData`), который Telegram добавляет сам. SDK инициализируется в
`src/telegram/init.ts` без внешних скриптов. Вне Telegram (dev, Playwright)
поднимается `mockTelegramEnv` с синтетическими launch params (`?mock=1` в prod-сборке).

**Последствия.** Нет поддержки очень старых клиентов, где launch params не
передаются в хэше (Bot API < 6.1, 2022). Для целевой аудитории это неактуально.
Если понадобится `window.Telegram.WebApp`, скрипт можно добавить с `defer`,
не ломая текущий код.

## ADR-002. Landscape lock: Telegram + Screen Orientation API + CSS-фолбэк

**Проблема.** В `@telegram-apps/sdk` 3.11.8 отсутствует метод `lockOrientation`,
хотя в Bot API 8.0 есть `web_app_toggle_orientation_lock`. Кроме того, этот метод
фиксирует **текущую** ориентацию, а iOS вообще не поддерживает `screen.orientation.lock`.

**Решение.** `src/mobile/orientation.ts`:
1. `screen.orientation.lock('landscape')` (Android Chrome в fullscreen) — best effort;
2. `postEvent('web_app_toggle_orientation_lock', { locked: true })` только если
   устройство уже в landscape (иначе зафиксируем портрет);
3. при возврате из фона лок переустанавливается (`visibilitychange`);
4. постоянный CSS-оверлей «Поверните телефон» (`OrientationOverlay`) — источник
   истины для UX, потому что лок может быть недоступен.

**Последствия.** В iOS Telegram игрок физически может держать телефон вертикально —
игра покажет оверлей и не запустит рендер. Это соответствует требованию «только landscape».

## ADR-003. Один canvas и один WebGL-контекст на всю сессию

**Проблема.** Пересоздание `WebGLRenderer` при переходе между экранами стоит
300–800 мс на мобильных GPU (компиляция шейдеров, upload текстур).

**Решение.** `<GameCanvas>` монтируется один раз в `App`, владелец — синглтон
`gameHost` (`src/game/GameHost.ts`). Экраны только показывают/скрывают слой и
вызывают `start/pause`. Движок создаётся при старте приложения, чтобы splash
показывал реальный прогресс, а не имитацию.

**Последствия.** React StrictMode в dev дважды монтирует эффекты — `GameHost.boot()`
дедуплицирует промис. `dispose()` движка вызывать только при выгрузке приложения.

## ADR-004. EffectComposer работает в CSS-пикселях

**Проблема.** `EffectComposer.setSize()` сам умножает переданные размеры на pixel
ratio рендерера. Если передать размер drawing buffer, получим двойное масштабирование
(и, например, 2.5× вместо 1.49× на medium).

**Решение.** В `Engine.resize()` композеру передаются CSS-размеры; `PostFX.setSize`
внутри вычисляет физический размер и отдаёт его проходам, которым нужны реальные
таргеты (SSAO, FXAA, bloom). `PostFX.bufferSize()` — единственное место, где
читается drawing buffer.

**Последствия.** Render scale работает предсказуемо; при смене пресета достаточно
вызвать `resize()`.

## ADR-005. Авто-качество с гистерезисом и защитой от осцилляции

**Проблема.** Наивное «FPS < 45 → понизить» даёт мигание пресетов на границе,
особенно на тёплом телефоне под троттлингом.

**Решение.** Чистая функция `decideQuality()` (тестируется без таймеров) +
`QualityController`:
- FPS считается окнами по 500 мс с EMA, первый экран отбрасывается (шейдеры компилируются);
- понижение — после 2 с ниже порога, повышение — после 6 с выше порога;
- между переключениями минимум 8 с, во время паузы решения не принимаются;
- ручной выбор в настройках отключает авто-режим.

**Последствия.** Пресет не «дрожит»; деградация занимает до ~8 с — приемлемо,
потому что первое понижение происходит в первые секунды после просадки.

## ADR-006. Интенсивность вибрации как понижение стиля

**Проблема.** Telegram Haptic API не имеет амплитуды: только `light/medium/heavy`,
`success/warning/error`, `selection`.

**Решение.** `src/telegram/haptic.ts` масштабирует интенсивность 0…1 через
даунгрейд стиля (< 0.75: heavy→medium, medium→light; < 0.4: всегда light; 0: выкл),
плюс троттлинг 32 мс против спама. `navigator.vibrate` не используется нигде.

**Последствия.** Настройка «вибро-интенсивность» влияет на «вес» отклика, а не на
физическую силу. Это документировано в UI-подсказке.

## ADR-007. Процедурные текстуры — общий код рантайма и офлайн-пайплайна

**Проблема.** Хочется одного вида ассетов и в тестовой сцене, и в финальных KTX2.

**Решение.** `src/game/visual/textures/noise.ts` + `normalMap.ts` — чистые функции
без DOM (покрыты Vitest). `proceduralTextures.ts` оборачивает их в CanvasTexture
для рантайма; этап 5 переиспользует те же генераторы в `scripts/textures/` для
офлайн-сборки PNG → KTX2.

**Последствия.** Placeholder — не «затычка», а первый класс ассетов; замена на
KTX2 не меняет внешний вид.

## ADR-008. Почему в HUD этапа 1 стоят эмодзи

**Проблема.** На этапе 1 нет пайплайна собственных UI-иконок (этап 12).

**Решение.** Кнопки меню/паузы используют системные эмодзи, но уже имеют
touch-таргеты 48×48 и haptic-отклик. Все иконки будут заменены SVG-атласом,
сгенерированным скриптом, на этапе визуального полиша.

**Последствия.** Эмодзи выглядят по-разному на iOS/Android — допустимо только
до этапа 12 и зафиксировано в CREDITS.

## ADR-009. Тесты: Vitest для математики, Playwright для устройства

**Проблема.** WebGL в headless-среде нестабилен, а мобильные жесты нельзя
проверить юнит-тестами.

**Решение.** Юнит-тесты покрывают чистые функции (камера, пресеты качества,
нормализация текстуры, safe-area, тема). Playwright запускается на профилях
Pixel 7 и iPhone 13 (landscape) с двумя движками; проверяются boot, живой рендер
(счётчик FPS двигается), пауза и блокировка в портрете.

**Последствия.** E2E требует `npx playwright install`; в CI браузеры ставятся
шагом workflow. SwiftShader-флаги дают детерминированный WebGL на раннерах.

## ADR-010. Ввод строится на зонах + pointerId, а не на «кнопках поверх всего»

**Проблема.** Нужны одновременные жесты: движение стиком, вращение камеры вторым
пальцем и удар третьим. Глобальный обработчик `pointerdown` на документе с ручной
маршрутизацией быстро превращается в спагетти и ломает захват указателя.

**Решение.** `InputLayer` (`src/input/InputLayer.tsx`) состоит из трёх независимых
элементов:
1. `stick-zone` — половина экрана под большой палец стика (низ, 66 % высоты);
2. `camera-zone` — противоположная половина, свайп и пинч;
3. кластер кнопок (`TouchButton`) поверх, `z-20`.

Каждый элемент получает свой `pointerId`, вызывает `setPointerCapture` (в try/catch —
синтетические указатели в тестах не захватываются) и игнорирует чужие id. Браузер сам
обеспечивает «маршрутизацию» по элементам, поэтому три пальца не конфликтуют.

**Последствия.** Жест, начатый в зоне камеры и уведённый на кнопку, всё равно остаётся
жестом камеры — это ожидаемое поведение и защищает от случайных срабатываний.

## ADR-011. Логика ввода — чистые классы, DOM — только представление

**Проблема.** Стик/свайп/кулдауны легко превратить в «магию» внутри React-компонента,
которую невозможно протестировать без браузера и которая ре-рендерит 60 fps.

**Решение.** `VirtualJoystick`, `CameraSwipe`, `CooldownTracker`, `cameraRelativeMove`
не знают про DOM. `JoystickView` пишет `transform` из rAF-цикла напрямую в DOM, кулдаун
кнопки — CSS-переменная `--cd-deg`, React ре-рендерится только при смене активного жеста.
Часы инжектируются (`nowMs`), поэтому тесты детерминированы (74 юнит-теста).

**Последствия.** Логику можно переиспользовать в E2E через тот же код; перенос
кулдаунов в боевую систему (этап 6) затронет только источник данных.

## ADR-012. E2E многопальцевый ввод — синтетические PointerEvent

**Проблема.** `page.touchscreen` умеет только одну точку; `Input.dispatchTouchEvent`
через CDP доступен лишь в Chromium, а WebKit — обязательная цель (iOS WebView).

**Решение.** Тесты `tests/e2e/touch.spec.ts` диспатчат `PointerEvent` с разными
`pointerId` прямо в зоны. Игровой слой читает только PointerEvents, поэтому путь
исполнения идентичен реальному; утверждения читают состояние через dev-мост
`window.__TENEBRIS__` (устанавливается только в DEV-сборке).

**Последствия.** Тест не проверяет системные жесты браузера (pinch-zoom страницы),
но это закрыто глобальными guard'ами (`touch-action: none`, `gesturestart`).

## ADR-013. Физика — фиксированный шаг 60 Гц, отдельный чанк, kinematic-капсула

**Проблема.** Character controller в Rapier работает по «свипу» капсулы на заданное
смещение. При переменном `dt` (90/120 Гц экраны, просадки) шаг движения гуляет,
капсула начинает застревать в углах и «телепортироваться» сквозь тонкие стены.

**Решение.**
- `FixedStepAccumulator` копит время кадра и выдаёт целое число шагов по 1/60 с,
  не больше 4 за кадр (лишнее время отбрасывается, а не копится — иначе спираль смерти).
  На паузе аккумулятор сбрасывается.
- `CharacterBody` — `kinematicPositionBased` тело + `KinematicCharacterController`
  (offset 0.02, autostep 0.35 м, snap-to-ground 0.3 м, уклон ≤50°). Каждый шаг:
  `computeColliderMovement` → `computedMovement` → `setNextKinematicTranslation`.
- Движение героя выполняется в `GameScene.fixedUpdate`, визуал и анимации — в
  `update(dt)` по реальному времени кадра.
- Rapier импортируется динамически (`PhysicsWorld.create()`), поэтому ~4 МБ WASM
  не попадают в стартовый чанк: в сборке это отдельный файл `rapier-*.js`, который
  грузится на стадии «Движок» сплэша.

**Последствия.** Ввод и камера не зависят от физики; на 120 Гц картинка плавная,
симуляция стабильная. `primeQueries()` (один `world.step()` после сборки сцены) нужен,
чтобы статические коллайдеры попали в query pipeline до первого raycast — иначе
камера на первом кадре проедет сквозь стену. Пакет — `rapier3d-compat` по ТЗ:
WASM встроен в base64, цена — chunk 1.67 МБ gzip вместо ~0.7 МБ у внешнего .wasm;
бюджет 3 МБ соблюдён, но это главный кандидат на оптимизацию в этапе 13.

## ADR-014. Коллайдеры строятся из тех же данных, что и меши

**Проблема.** Рассинхрон визуала и физики (стена нарисована в одном месте, коллайдер
в другом) — классический источник «прохожу сквозь стену» и «застрял в воздухе».

**Решение.** В `TestScene` позиции стен/колонн задаются массивами, и из каждого
элемента создаётся и меш, и статический коллайдер (`addStaticBox`/`addStaticCylinder`).
Коллайдер колонны чуть шире визуального конуса, чтобы капсула не задевала визуал.
В этапе 4 генератор подземелья будет возвращать единый список `{type, position,
halfExtents}` — физика и инстансы мешей будут строиться из него.

**Последствия.** Камера-raycast использует физику, а не обход сцены: попадания
совпадают с реальными препятствиями и это дешевле.

## ADR-015. Подземелье — чистый генератор + отдельные слои меша/физики/света

**Проблема.** Генератор, который сам создаёт `Mesh` и коллайдеры, невозможно
протестировать в Node и почти невозможно отлаживать: ошибка в BSP выглядит как
«странная геометрия», а не как упавший тест.

**Решение.** Этап 4 разбит на четыре независимых модуля:
1. `world/bsp.ts` — BSP, нарезка листьев, выбор комнат, MST (+ 1–2 петли), RNG
   (`mulberry32`). Чистые функции, никакого three.js.
2. `world/DungeonGenerator.ts` — `generate({seed, floor})` → `Dungeon`
   (сетка `tiles`/`roomIds`/`ceiling`, комнаты, двери, вход, выход). Шесть
   детерминированных попыток (сид производный: `seed + floor*7919 + attempt*104729`),
   затем простой fallback. Каждая попытка проходит ворота связности (флуд-филл): пол
   либо полностью проходим, либо отбрасывается.
3. `world/DungeonMesh.ts` — `buildDungeonMesh(dungeon, physics, materials)`:
   три merged-меша (пол/стены/потолок) и коллайдеры из тех же данных.
4. `world/Door.ts`, `world/Props.ts`, `world/RoomLights.ts` — двери, мебель, свет.

**Последствия.** Генерация тестируется на 500 сидах за ~4 с, геометрия — headless
(three собирает `BufferGeometry` без GL-контекста), а `DungeonScene` склеивает слои
и остаётся тонким адаптером (как `TestScene` в этапе 3).

## ADR-016. UV в мировых координатах, коллайдеры — жадными прямоугольниками

**Проблема.** Пол из ~700 тайлов даёт 700 квадов; если UV считать локально, текстура
перезапускается на каждом квадратном метре и шов виден как сетка. Если делать
коллайдер на тайл — это ~700 статических тел и столько же в broadphase, что бьёт по
шагу физики и по raycast камеры.

**Решение.**
- `pushQuad` выводит UV из мировых координат (плоскость выбирается по нормали:
  пол — `(x,z)`, X-стена — `(z,y)`, Z-стена — `(x,y)`), 0.5 UV на метр. Одна
  текстура 256² с `RepeatWrapping` покрывает весь этаж без швов.
- `gridRects.greedyRectangles(mask, w, h)` сливает маску в прямоугольники: стены —
  один слой высотой 6 м, потолки — по слоям высоты (`CEILING_STEP = 0.5`), пол —
  один бокс. На реальном этаже это 40–70 коллайдеров вместо ~2000.
- Стена над низкой соседней комнатой рисуется отдельным квадом (иначе из низкой
  комнаты видно «дыру» в стене высокой).

**Последствия.** 3 draw call на геометрию этажа, ~50 коллайдеров, UV-плотность
одинаковая на всех поверхностях. Мебель добаляет ~10 instanced draw call'ов,
двери — по 4–6 мешей на проём (геометрия общая на весь этаж).

## ADR-017. Бюджет света: комната = один PointLight, видимы только ближайшие

**Проблема.** 7 комнат × факелы + герой + выход — при наивном подходе 20+ point
lights, и каждый из них участвует в шейдере PBR всех материалов. Это главный
убийца fill rate на мобильных GPU, особенно в сочетании с bloom.

**Решение.** `RoomLights` держит по одному свету на комнату (цвет/интенсивность/
радиус из `rooms.json`) и включает только N ближайших к игроку; пересчёт — 5 раз в
секунду, а не каждый кадр. Свой факел героя всегда включён, поэтому в коридоре не
темно. Бюджет тарифа (`maxPointLights`) уменьшается на 1 — этот слот зарезервирован
под свет руны выхода, который включается в радиусе 12 м. Мебель и факелы **не
создают** источников света: их огонь — emissive-геометрия + bloom, а мерцание
приходит от света комнаты.

**Последствия.** На high/medium ≤4 активных point light, на low — 2 (только факел
героя). `DebugSceneSnapshot.activeLights` позволяет E2E-тесту поймать регрессию.

## ADR-018. Двери — физика включается только у закрытой створки

**Проблема.** Дверь в подземелье должна и открываться, и не пропускать капсулу
сквозь закрытую створку; при этом нельзя «защемить» игрока в проёме, если он успел
войти до окончания анимации.

**Решение.** `Doorway` — два коллайдера-состояния в одном: статический бокс
существует всегда, но `setEnabled` включается только при `open < 0.12` И дистанции
до игрока > 1.4 м. Открытие — 3.2 м, закрытие — 4.4 м (гистерезис, чтобы створка не
хлопала на границе). Створки (1–2, в зависимости от ширины) вращаются вокруг
петельных групп на 90°, геометрия панелей кешируется по ширине на весь этаж.

**Последствия.** Стоимость: один query-вызов `isEnabled()` за дверь за кадр
(10–19 дверей на этаж). Двери удаляют свой коллайдер в `dispose()`, поэтому спуск
на новый этаж не оставляет фантомных стен.
