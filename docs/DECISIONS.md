# Архитектурные решения (ADR)

Формат: **проблема → решение → последствия**. Все записи обязательны к прочтению
перед изменением соответствующего слоя.

## ADR-001. Не подключаем `telegram-web-app.js` с CDN

**Проблема.** Классическая интеграция требует `<script src="https://telegram.org/js/telegram-web-app.js">`,
это блокирующий сторонний запрос на критическом пути первого рендера (< 2.5 с) и
лишняя точка отказа (в WebView с плохой сетью скрипт может не загрузиться).

**Решение.** `@telegram-apps/sdk` v3 читает launch params из URL-хэша
(`tgWebAppData`), который Telegram добавляет сам. SDK инициализируется в
`src/telegram/init.ts` без внешних скриптов. Вне Telegram (dev, Playwright)
поднимается `mockTelegramEnv` с синтетическими launch params (`?mock=1` в prod-сборке).

**Последствия.** Нет поддержки очень старых клиентов, где launch params не
передаются в хэше (Bot API < 6.1, 2022). Для целевой аудитории это неактуально.
Если понадобится `window.Telegram.WebApp`, скрипт можно добавить с `defer`,
не ломая текущий код.

## ADR-002. Landscape lock: Telegram + Screen Orientation API + CSS-фолбэк

**Проблема.** В `@telegram-apps/sdk` 3.11.8 отсутствует метод `lockOrientation`,
хотя в Bot API 8.0 есть `web_app_toggle_orientation_lock`. Кроме того, этот метод
фиксирует **текущую** ориентацию, а iOS вообще не поддерживает `screen.orientation.lock`.

**Решение.** `src/mobile/orientation.ts`:
1. `screen.orientation.lock('landscape')` (Android Chrome в fullscreen) — best effort;
2. `postEvent('web_app_toggle_orientation_lock', { locked: true })` только если
   устройство уже в landscape (иначе зафиксируем портрет);
3. при возврате из фона лок переустанавливается (`visibilitychange`);
4. постоянный CSS-оверлей «Поверните телефон» (`OrientationOverlay`) — источник
   истины для UX, потому что лок может быть недоступен.

**Последствия.** В iOS Telegram игрок физически может держать телефон вертикально —
игра покажет оверлей и не запустит рендер. Это соответствует требованию «только landscape».

## ADR-003. Один canvas и один WebGL-контекст на всю сессию

**Проблема.** Пересоздание `WebGLRenderer` при переходе между экранами стоит
300–800 мс на мобильных GPU (компиляция шейдеров, upload текстур).

**Решение.** `<GameCanvas>` монтируется один раз в `App`, владелец — синглтон
`gameHost` (`src/game/GameHost.ts`). Экраны только показывают/скрывают слой и
вызывают `start/pause`. Движок создаётся при старте приложения, чтобы splash
показывал реальный прогресс, а не имитацию.

**Последствия.** React StrictMode в dev дважды монтирует эффекты — `GameHost.boot()`
дедуплицирует промис. `dispose()` движка вызывать только при выгрузке приложения.

## ADR-004. EffectComposer работает в CSS-пикселях

**Проблема.** `EffectComposer.setSize()` сам умножает переданные размеры на pixel
ratio рендерера. Если передать размер drawing buffer, получим двойное масштабирование
(и, например, 2.5× вместо 1.49× на medium).

**Решение.** В `Engine.resize()` композеру передаются CSS-размеры; `PostFX.setSize`
внутри вычисляет физический размер и отдаёт его проходам, которым нужны реальные
таргеты (SSAO, FXAA, bloom). `PostFX.bufferSize()` — единственное место, где
читается drawing buffer.

**Последствия.** Render scale работает предсказуемо; при смене пресета достаточно
вызвать `resize()`.

## ADR-005. Авто-качество с гистерезисом и защитой от осцилляции

**Проблема.** Наивное «FPS < 45 → понизить» даёт мигание пресетов на границе,
особенно на тёплом телефоне под троттлингом.

**Решение.** Чистая функция `decideQuality()` (тестируется без таймеров) +
`QualityController`:
- FPS считается окнами по 500 мс с EMA, первый экран отбрасывается (шейдеры компилируются);
- понижение — после 2 с ниже порога, повышение — после 6 с выше порога;
- между переключениями минимум 8 с, во время паузы решения не принимаются;
- ручной выбор в настройках отключает авто-режим.

**Последствия.** Пресет не «дрожит»; деградация занимает до ~8 с — приемлемо,
потому что первое понижение происходит в первые секунды после просадки.

## ADR-006. Интенсивность вибрации как понижение стиля

**Проблема.** Telegram Haptic API не имеет амплитуды: только `light/medium/heavy`,
`success/warning/error`, `selection`.

**Решение.** `src/telegram/haptic.ts` масштабирует интенсивность 0…1 через
даунгрейд стиля (< 0.75: heavy→medium, medium→light; < 0.4: всегда light; 0: выкл),
плюс троттлинг 32 мс против спама. `navigator.vibrate` не используется нигде.

**Последствия.** Настройка «вибро-интенсивность» влияет на «вес» отклика, а не на
физическую силу. Это документировано в UI-подсказке.

## ADR-007. Процедурные текстуры — общий код рантайма и офлайн-пайплайна

**Проблема.** Хочется одного вида ассетов и в тестовой сцене, и в финальных KTX2.

**Решение.** `src/game/visual/textures/noise.ts` + `normalMap.ts` — чистые функции
без DOM (покрыты Vitest). `proceduralTextures.ts` оборачивает их в CanvasTexture
для рантайма; этап 5 переиспользует те же генераторы в `scripts/textures/` для
офлайн-сборки PNG → KTX2.

**Последствия.** Placeholder — не «затычка», а первый класс ассетов; замена на
KTX2 не меняет внешний вид.

## ADR-008. Почему в HUD этапа 1 стоят эмодзи

**Проблема.** На этапе 1 нет пайплайна собственных UI-иконок (этап 12).

**Решение.** Кнопки меню/паузы используют системные эмодзи, но уже имеют
touch-таргеты 48×48 и haptic-отклик. Все иконки будут заменены SVG-атласом,
сгенерированным скриптом, на этапе визуального полиша.

**Последствия.** Эмодзи выглядят по-разному на iOS/Android — допустимо только
до этапа 12 и зафиксировано в CREDITS.

## ADR-009. Тесты: Vitest для математики, Playwright для устройства

**Проблема.** WebGL в headless-среде нестабилен, а мобильные жесты нельзя
проверить юнит-тестами.

**Решение.** Юнит-тесты покрывают чистые функции (камера, пресеты качества,
нормализация текстуры, safe-area, тема). Playwright запускается на профилях
Pixel 7 и iPhone 13 (landscape) с двумя движками; проверяются boot, живой рендер
(счётчик FPS двигается), пауза и блокировка в портрете.

**Последствия.** E2E требует `npx playwright install`; в CI браузеры ставятся
шагом workflow. SwiftShader-флаги дают детерминированный WebGL на раннерах.

## ADR-010. Ввод строится на зонах + pointerId, а не на «кнопках поверх всего»

**Проблема.** Нужны одновременные жесты: движение стиком, вращение камеры вторым
пальцем и удар третьим. Глобальный обработчик `pointerdown` на документе с ручной
маршрутизацией быстро превращается в спагетти и ломает захват указателя.

**Решение.** `InputLayer` (`src/input/InputLayer.tsx`) состоит из трёх независимых
элементов:
1. `stick-zone` — половина экрана под большой палец стика (низ, 66 % высоты);
2. `camera-zone` — противоположная половина, свайп и пинч;
3. кластер кнопок (`TouchButton`) поверх, `z-20`.

Каждый элемент получает свой `pointerId`, вызывает `setPointerCapture` (в try/catch —
синтетические указатели в тестах не захватываются) и игнорирует чужие id. Браузер сам
обеспечивает «маршрутизацию» по элементам, поэтому три пальца не конфликтуют.

**Последствия.** Жест, начатый в зоне камеры и уведённый на кнопку, всё равно остаётся
жестом камеры — это ожидаемое поведение и защищает от случайных срабатываний.

## ADR-011. Логика ввода — чистые классы, DOM — только представление

**Проблема.** Стик/свайп/кулдауны легко превратить в «магию» внутри React-компонента,
которую невозможно протестировать без браузера и которая ре-рендерит 60 fps.

**Решение.** `VirtualJoystick`, `CameraSwipe`, `CooldownTracker`, `cameraRelativeMove`
не знают про DOM. `JoystickView` пишет `transform` из rAF-цикла напрямую в DOM, кулдаун
кнопки — CSS-переменная `--cd-deg`, React ре-рендерится только при смене активного жеста.
Часы инжектируются (`nowMs`), поэтому тесты детерминированы (74 юнит-теста).

**Последствия.** Логику можно переиспользовать в E2E через тот же код; перенос
кулдаунов в боевую систему (этап 6) затронет только источник данных.

## ADR-012. E2E многопальцевый ввод — синтетические PointerEvent

**Проблема.** `page.touchscreen` умеет только одну точку; `Input.dispatchTouchEvent`
через CDP доступен лишь в Chromium, а WebKit — обязательная цель (iOS WebView).

**Решение.** Тесты `tests/e2e/touch.spec.ts` диспатчат `PointerEvent` с разными
`pointerId` прямо в зоны. Игровой слой читает только PointerEvents, поэтому путь
исполнения идентичен реальному; утверждения читают состояние через dev-мост
`window.__TENEBRIS__` (устанавливается только в DEV-сборке).

**Последствия.** Тест не проверяет системные жесты браузера (pinch-zoom страницы),
но это закрыто глобальными guard'ами (`touch-action: none`, `gesturestart`).

## ADR-013. Физика — фиксированный шаг 60 Гц, отдельный чанк, kinematic-капсула

**Проблема.** Character controller в Rapier работает по «свипу» капсулы на заданное
смещение. При переменном `dt` (90/120 Гц экраны, просадки) шаг движения гуляет,
капсула начинает застревать в углах и «телепортироваться» сквозь тонкие стены.

**Решение.**
- `FixedStepAccumulator` копит время кадра и выдаёт целое число шагов по 1/60 с,
  не больше 4 за кадр (лишнее время отбрасывается, а не копится — иначе спираль смерти).
  На паузе аккумулятор сбрасывается.
- `CharacterBody` — `kinematicPositionBased` тело + `KinematicCharacterController`
  (offset 0.02, autostep 0.35 м, snap-to-ground 0.3 м, уклон ≤50°). Каждый шаг:
  `computeColliderMovement` → `computedMovement` → `setNextKinematicTranslation`.
- Движение героя выполняется в `GameScene.fixedUpdate`, визуал и анимации — в
  `update(dt)` по реальному времени кадра.
- Rapier импортируется динамически (`PhysicsWorld.create()`), поэтому ~4 МБ WASM
  не попадают в стартовый чанк: в сборке это отдельный файл `rapier-*.js`, который
  грузится на стадии «Движок» сплэша.

**Последствия.** Ввод и камера не зависят от физики; на 120 Гц картинка плавная,
симуляция стабильная. `primeQueries()` (один `world.step()` после сборки сцены) нужен,
чтобы статические коллайдеры попали в query pipeline до первого raycast — иначе
камера на первом кадре проедет сквозь стену. Пакет — `rapier3d-compat` по ТЗ:
WASM встроен в base64, цена — chunk 1.67 МБ gzip вместо ~0.7 МБ у внешнего .wasm;
бюджет 3 МБ соблюдён, но это главный кандидат на оптимизацию в этапе 13.

## ADR-014. Коллайдеры строятся из тех же данных, что и меши

**Проблема.** Рассинхрон визуала и физики (стена нарисована в одном месте, коллайдер
в другом) — классический источник «прохожу сквозь стену» и «застрял в воздухе».

**Решение.** В `TestScene` позиции стен/колонн задаются массивами, и из каждого
элемента создаётся и меш, и статический коллайдер (`addStaticBox`/`addStaticCylinder`).
Коллайдер колонны чуть шире визуального конуса, чтобы капсула не задевала визуал.
В этапе 4 генератор подземелья будет возвращать единый список `{type, position,
halfExtents}` — физика и инстансы мешей будут строиться из него.

**Последствия.** Камера-raycast использует физику, а не обход сцены: попадания
совпадают с реальными препятствиями и это дешевле.

## ADR-015. Подземелье — чистый генератор + отдельные слои меша/физики/света

**Проблема.** Генератор, который сам создаёт `Mesh` и коллайдеры, невозможно
протестировать в Node и почти невозможно отлаживать: ошибка в BSP выглядит как
«странная геометрия», а не как упавший тест.

**Решение.** Этап 4 разбит на четыре независимых модуля:
1. `world/bsp.ts` — BSP, нарезка листьев, выбор комнат, MST (+ 1–2 петли), RNG
   (`mulberry32`). Чистые функции, никакого three.js.
2. `world/DungeonGenerator.ts` — `generate({seed, floor})` → `Dungeon`
   (сетка `tiles`/`roomIds`/`ceiling`, комнаты, двери, вход, выход). Шесть
   детерминированных попыток (сид производный: `seed + floor*7919 + attempt*104729`),
   затем простой fallback. Каждая попытка проходит ворота связности (флуд-филл): пол
   либо полностью проходим, либо отбрасывается.
3. `world/DungeonMesh.ts` — `buildDungeonMesh(dungeon, physics, materials)`:
   три merged-меша (пол/стены/потолок) и коллайдеры из тех же данных.
4. `world/Door.ts`, `world/Props.ts`, `world/RoomLights.ts` — двери, мебель, свет.

**Последствия.** Генерация тестируется на 500 сидах за ~4 с, геометрия — headless
(three собирает `BufferGeometry` без GL-контекста), а `DungeonScene` склеивает слои
и остаётся тонким адаптером (как `TestScene` в этапе 3).

## ADR-016. UV в мировых координатах, коллайдеры — жадными прямоугольниками

**Проблема.** Пол из ~700 тайлов даёт 700 квадов; если UV считать локально, текстура
перезапускается на каждом квадратном метре и шов виден как сетка. Если делать
коллайдер на тайл — это ~700 статических тел и столько же в broadphase, что бьёт по
шагу физики и по raycast камеры.

**Решение.**
- `pushQuad` выводит UV из мировых координат (плоскость выбирается по нормали:
  пол — `(x,z)`, X-стена — `(z,y)`, Z-стена — `(x,y)`), 0.5 UV на метр. Одна
  текстура 256² с `RepeatWrapping` покрывает весь этаж без швов.
- `gridRects.greedyRectangles(mask, w, h)` сливает маску в прямоугольники: стены —
  один слой высотой 6 м, потолки — по слоям высоты (`CEILING_STEP = 0.5`), пол —
  один бокс. На реальном этаже это 40–70 коллайдеров вместо ~2000.
- Стена над низкой соседней комнатой рисуется отдельным квадом (иначе из низкой
  комнаты видно «дыру» в стене высокой).

**Последствия.** 3 draw call на геометрию этажа, ~50 коллайдеров, UV-плотность
одинаковая на всех поверхностях. Мебель добаляет ~10 instanced draw call'ов,
двери — по 4–6 мешей на проём (геометрия общая на весь этаж).

## ADR-017. Бюджет света: комната = один PointLight, видимы только ближайшие

**Проблема.** 7 комнат × факелы + герой + выход — при наивном подходе 20+ point
lights, и каждый из них участвует в шейдере PBR всех материалов. Это главный
убийца fill rate на мобильных GPU, особенно в сочетании с bloom.

**Решение.** `RoomLights` держит по одному свету на комнату (цвет/интенсивность/
радиус из `rooms.json`) и включает только N ближайших к игроку; пересчёт — 5 раз в
секунду, а не каждый кадр. Свой факел героя всегда включён, поэтому в коридоре не
темно. Бюджет тарифа (`maxPointLights`) уменьшается на 1 — этот слот зарезервирован
под свет руны выхода, который включается в радиусе 12 м. Мебель и факелы **не
создают** источников света: их огонь — emissive-геометрия + bloom, а мерцание
приходит от света комнаты.

**Последствия.** На high/medium ≤4 активных point light, на low — 2 (только факел
героя). `DebugSceneSnapshot.activeLights` позволяет E2E-тесту поймать регрессию.

## ADR-018. Двери — физика включается только у закрытой створки

**Проблема.** Дверь в подземелье должна и открываться, и не пропускать капсулу
сквозь закрытую створку; при этом нельзя «защемить» игрока в проёме, если он успел
войти до окончания анимации.

**Решение.** `Doorway` — два коллайдера-состояния в одном: статический бокс
существует всегда, но `setEnabled` включается только при `open < 0.12` И дистанции
до игрока > 1.4 м. Открытие — 3.2 м, закрытие — 4.4 м (гистерезис, чтобы створка не
хлопала на границе). Створки (1–2, в зависимости от ширины) вращаются вокруг
петельных групп на 90°, геометрия панелей кешируется по ширине на весь этаж.

**Последствия.** Стоимость: один query-вызов `isEnabled()` за дверь за кадр
(10–19 дверей на этаж). Двери удаляют свой коллайдер в `dispose()`, поэтому спуск
на новый этаж не оставляет фантомных стен.

## ADR-019. Ассеты — код: THREE-геометрия + GLTFExporter, Blender не нужен

**Проблема.** ТЗ требует скелетной анимации (`AnimationMixer` + клипы) и при этом
«все ассеты генерируются скриптами в репозитории». Blender нет ни в CI, ни в
окружении разработки, а `.blend`-файлы не являются воспроизводимым артефактом.

**Решение.** `npm run assets` (`scripts/build-assets.ts`) собирает модели
целиком в Node:
- `scripts/models/rig.ts` — арматура: кости создаются с identity-вращением и
  смещением только от родителя, поэтому локальные оси кости совпадают с мировыми
  и анимация пишется обычными углами Эйлера;
- `scripts/models/skinBuilder.ts` — жёсткие «доспешные» веса (1–2 кости на
  вершину, узкая полоса смешивания у сустава) — стилизованный вид, ~1.3k
  треугольников на героя и тривиально проверяемая матрица весов;
- `scripts/models/hero.ts`, `monster.ts`, `props.ts` — сами модели и семь клипов
  героя (`idle/walk/run/attack/dodge/hit/death`);
- `scripts/models/glb.ts` — экспорт через `GLTFExporter` и shim `FileReader`
  (Node 22 не имеет его, а экспортёр читает результат через него).

**Последствия.** GLB не коммитятся (`.gitignore`): `predev`/`prebuild` и шаг CI
«Build assets» пересобирают их за ~90 мс. Пайплайн сам валидирует результат
(`inspectGlb`: магия, версия, наличие скина и всех клипов) и падает, если модель
сломана. Тесты `assetPipeline.test.ts` прогоняют генераторы, читают GLB байтами и
заново загружают его тем же `GLTFLoader`, что и игра: имена костей, клипы, веса,
inverse bind-матрицы, рост модели. Blender остаётся опциональным путём
(`scripts/blender/README.md`) с тем же контрактом имён.

## ADR-020. Анимация — конечный автомат с одной ногой в геймплее

**Проблема.** Клип атаки (0.55 с) не совпадает с геймплейным окном удара
(0.28 с), а рваные `crossFade` в сцене превращают персонажа в «слайд-шоу» при
одновременном движении, ударе и рывке.

**Решение.** `CharacterModel` (`src/game/entities/CharacterModel.ts`):
- локомоция `idle/walk/run` выбирается по скорости м/с с порогами 0.08/4.2;
- одноразовые действия (`attack`, `dodge`, `hit`) забирают тело, проигрываются
  `LoopOnce` и возвращают управление по событию `finished` микшера;
- клипы атаки и рывка масштабируются по времени (`timeScale`) под геймплейные
  окна, чтобы удар визуально попадал в момент урона;
- `hit` не сбивает `attack` (иначе чип-урон отменял бы замах);
- `death` терминальна и удерживает последний кадр;
- отсутствующий клип не ломает автомат — действие просто не запускается.

Сцена передаёт только числа: `hero.update(dt, elapsed, speed, busy)`, а
`attack`/`dodge` вызывает по фронтам состояния контроллера, поэтому один и тот же
компонент обслуживает героя и монстров (этап 6).

**Последствия.** Геймплейные таймеры остаются в `PlayerController`
(`PLAYER_TUNING.attackDuration`), визуал — в модели; тесты стейт-машины не
требуют ни браузера, ни ассетов (синтетические клипы). Если GLB не загрузился,
сцена молча переключается на placeholder-капсулу (`HeroView`) и остаётся
играбельной.

## ADR-021. Боёвка: чистые правила отдельно от сцены, тела врагов — по требованию

**Проблема.** Боёвка — первое место, где мобильный бюджет встречается с
геймплеем: нужно одновременно (а) держать предсказуемый урон, который можно
проверить без браузера, (б) не держать на сцене двадцать скелетов со
скиннингом, (в) не читать React-состояние в кадре рендера и (г) оставить
возможность расширять контент без переписывания кода.

**Решение.** Правила вынесены в чистые модули без three.js и Rapier:

- `combat/Health` — единственная точка, где живут HP, броня и i-frames.
  Броня по кривой `armor/(armor+50)` с полом 20 % от сырого урона: сильная
  броня заметно режет урон, но не делает врага неуязвимым. I-frames отменяют
  удар целиком, а не уменьшают его — на тач-управлении полумеры читаются как
  баг.
- `combat/damage` — крит одним роллом, ±10 % разброса иначе. Возвращается
  *сырой* урон, митигация остаётся в `Health`, поэтому таблицы урона в JSON не
  дублируют формулы.
- `combat/meleeArc` — конус атаки игрока. Угловой допуск `atan2(radius, distance)`
  расширяет конус на размер тела цели: игрок целится стиком, а не курсором.
- `ai/EnemyBrain` — конечный автомат `idle → chase → windup → recover`, со
  стаггером, проверкой линии видимости и leash. Таймеры идут фиксированным
  шагом, поэтому поведение одинаково на 60 и 120 Гц.
- `data/monsters.json` + `combat/monsterTable` — контент (HP, броня, скорость,
  окна замаха/восстановления, XP, допустимые типы комнат). Новый монстр — это
  запись в JSON и модель в пайплайне ассетов, а не правка сцены.

`world/EnemyDirector` решает **когда** враги существуют: план населения этажа
детерминированно строится из сида подземелья (те же комнаты и точки спавна
всегда дают тех же врагов), но тела создаются только при подходе к комнате
(`activateRange`), удаляются при уходе (`deactivateRange`) и не появляются ближе
4 м к игроку. Потолок одновременных врагов — `maxActive = 6`, что удерживает
количество скиннинг-моделей, капсул и анимационных микшеров в предсказуемых
рамках. Убитый враг помечается в плане навсегда: зачищенная комната остаётся
пустой до перегенерации этажа.

**Последствия.** Все правила боёвки покрыты юнит-тестами (HP/броня/i-frames,
криты, конус, автомат ИИ, план спавна, стамина) и не требуют ни WebGL, ни
Rapier — сцена проверяется отдельным «headless» тестом, который крутит реальный
фиксированный шаг. Сцена владеет только исполнением: движение капсул, поворот к
цели, отдача (knockback), вызов урона и хуки обратной связи. HUD читает
снапшот через 10 Гц поллинг, а не через подписку на кадр, поэтому бой не
перерисовывает React. Смерть игрока пока — респавн у входа с полным
восстановлением и офф-сет i-frames; экран смерти и потеря лута придут вместе с
мета-прогрессией (этап 8/12), и `PlayerStats` уже отделён от сцены, чтобы это
не потребовало переписывания боёвки.

## ADR-022. Лут: контент в JSON, экономика в классе, панель — только читатель

**Проблема.** Снаряжение связывает три слоя, которые легко сшить намертво:
контент (что вообще может выпасть), правила (насколько сильнее редкий предмет и
как бонусы складываются со статами игрока) и интерфейс (список предметов и
кнопки «надеть»). Если UI читает игровые объекты напрямую, а бонусы считаются
в двух местах, балансировка превращается в переписывание кода.

**Решение.**
- `src/data/items.json` — единственный источник контента: 12 базовых предметов
  в трёх слотах, три редкости с множителем силы, диапазоны золота, шанс дропа с
  монстра, ёмкость сумки. Код не хранит ни одной цифры баланса.
- `loot/LootTable` — чистые функции роллов с инжектированным `roll()`: редкость
  выбирается взвешенно, предмет — равномерно из пула, разрешённого на текущем
  этаже (`minFloor`), поэтому глубина открывает новые базы, а не только числа.
- `loot/Inventory` — сумка фиксированной ёмкости и три слота. `equip()`
  возвращает вытесненный предмет в сумку, `unequip()` отказывает, если сумка
  полна, а `totals()` отдаёт одну агрегированную структуру бонусов.
- `loot/RunState` — золото, XP и инвентарь текущего забега. Наружу отдаёт только
  `snapshot()`: плоские сериализуемые строки для React. Это же сделает возможным
  сохранение забега в Dexie на этапе 12 без переписывания панели.
- `PlayerStats.applyBonuses()` — единственное место, где база складывается со
  снаряжением. `Health.setMax()` меняет максимум пула вместе с текущим HP, так
  что снятие амулета не оставляет игрока «выше максимума».
- Сундук — сущность (`entities/Chest`) с GLB-моделью, а не инстанс мебели:
  открывается один раз, выдаёт лут через тот же `RunState`, а «открытие»
  выражается пружинной анимацией корпуса (в экспортированной модели крышка
  спечена в меш, поэтому лид-костей нет — это осознанный компромисс против
  отдельного рига для пропса).

**Последствия.** Дроп с монстров и из сундуков идёт одним путём
(`RunState.grant`), поэтому переполнение сумки всегда репортится, а не теряется
молча. Панель инвентаря опрашивает снапшот раз в 150 мс, пока открыта, и ставит
игру на паузу: модальное окно не должно соседствовать с ударами монстров.
Таблица проверяется тестами (уникальные id, валидные слоты, растущий пул по
этажам), математика бонусов — тестами `PlayerStats`, а сквозной путь
«сундук → золото/предметы → надеть → выросший урон» — headless-тестом сцены.

## ADR-023. Голод как отдельные часы, смерть как конец забега

**Проблема.** Survival-механика легко превращается в «полоску, которая просто
убывает»: если голод ничего не меняет, он не нужен; если он убивает мгновенно,
игрок не понимает, за что умер. Отдельно стоял вопрос смерти: до этапа 8 игрок
возрождался у входа, что маскировало ошибки баланса и обесценивало лут.

**Решение.**
- Голод — самостоятельный класс `survival/Survival` с балансом в
  `src/data/survival.json` (скорость, пороги, множители, паёк, костёр). Он не
  знает ни про three.js, ни про сцену: `tick(dt, moving)` возвращает урон от
  истощения, `eat()` кормит, `tier` описывает состояние.
- Голод влияет на две вещи, которые игрок чувствует сразу: восстановление
  стамины (`PlayerStats.setRegenMultiplier`) и исходящий урон
  (`setDamageMultiplier`). Никаких скрытых дебаффов вроде «−5 % скорости»:
  игрок должен понимать, почему удар стал слабее.
- Еда — отдельный ресурс, а не предмет инвентаря. Пайки падают с монстров (24 %)
  и **всегда** лежат в сундуках; едятся одной кнопкой из HUD. Так сумка на 12
  слотов остаётся про снаряжение, а не про «съедобный мусор».
- Костёр — единственная точка восстановления: лечит 35 % HP, кормит на 22 и
  возвращает 60 стамины, но один раз за этаж и только если в радиусе 7 м нет
  живых врагов. Иначе отдых превращается в бесплатное лечение посреди боя.
- Смерть — конец забега. Сцена замораживает симуляцию (`fixedUpdate` выходит
  сразу), проигрывает клип смерти, отдаёт `onDeath(summary)` и больше ничего не
  делает. HUD показывает итоги и две кнопки: новый забег или меню.

**Последствия.** `restartRun()` пересоздаёт этаж и обнуляет забег (инвентарь,
золото, опыт, голод, счётчики), но **не** пересоздаёт движок, физику и WebGL-
контекст: на телефоне это разница между 50 мс и 500 мс. Из-за этого у героя
появился `revive()`, а у сцены — один явный список того, что сбрасывается; оба
покрыты тестами, включая «после рестарта снова 100 HP и полная сытость».
Экран итогов живёт в DOM поверх замороженной сцены, поэтому стоит 0 кадров
рендера. Цикл при смерти не останавливается — иначе клип смерти замирал бы на
первом кадре; ввод при этом отключён и в сцене, и в слое касаний.

## ADR-024. Босс как арена и эссенция как ответ на смерть

**Проблема.** Рогалик без финала превращается в бесконечный забег, а «мета»
без смерти — в копилку. Нужен был конец: одна цель на третьем этаже, которую
нельзя пройти, просто накопив лут, и награда за сам факт проигрыша.

**Решение.**
- Босс — обычный `MonsterDefinition` из `monsters.json` (`boss: true`, `phases`),
  а не отдельный класс. Он использует тот же `Enemy`, `EnemyBrain` и физику;
  отличий ровно два: фазы ярости и запрет на стаггер (телеграф удара должен
  оставаться честным, а не отменяться чип-уроном).
- Фазы считает чистая функция `ai/BossPhase.phaseMultipliers(hpRatio, phases)`.
  Пороги, множители скорости/урона/кулдауна и реплики лежат в данных, поэтому
  нового босса можно добавить без кода. `Enemy` уведомляет колбэком ровно один
  раз на порог — тост и тряска камеры не спамятся.
- Арена — самый дальний зал этажа, типизированный `boss` в генераторе. Тип
  `boss` специально имеет `weight: 0`: он никогда не выпадает в случайной
  раздаче комнат, иначе на третьем этаже могло не оказаться арены.
- Босс ставится в центр арены и **никогда** не выгружается по дистанции
  (`EnemyDirector.isBossSpawn`): отступление в коридор не должно «убивать»
  противника, у которого осталось 20 % HP.
- Смерть босса завершает забег как победа (`cause: 'victory'`), а не открывает
  лестницу: один финал проще читать, а экран итогов уже существует.
- Мета-прогрессия — `game/meta/MetaState`: чистый класс (эссенция-«угли»,
  уровни апгрейдов, стоимость, бонусы) поверх `MetaRepository` (таблица `meta`,
  ключ `progression`). Запись — сразу на покупку, без дебаунса: дебаунс-окно
  теряло покупку, если игрок закрывал мини-апп в те же 250 мс. Награда за забег — данные
  (`progression.json`): база за забег + убийства + этажи + сундуки + бонус за
  победу. Даже смерть на первом этаже приносит угли.
- Бонусы апгрейдов складываются со снаряжением в одном месте
  (`addBonuses(meta, inventory.totals())`) и применяются через уже существующий
  `PlayerStats.applyBonuses`, поэтому «купил живучесть» не создаёт второй
  стат-пайплайн.
- Итог забега пишется в таблицу `stats` (`StatsRepository`), а угли — в `meta`:
  история и экономика разделены, поэтому сброс прогресса не стирает статистику.

- Алтарь — не страница, а **оверлей** с собственным `AnimatePresence`.
  Главный `AnimatePresence` работает в `mode="wait"`: он обязан доиграть выход
  игрового экрана (200 мс) прежде чем монтировать следующий, и экран, попавший
  в эту паузу, оставлял мёртвую копию в DOM — по ней проходили нажатия (экономика
  менялась), но она уже не перерисовывалась. Собственный presence держит ровно
  одно дерево алтаря, а строки списка читаются из живого снапшота стора
  (`getState()`), поэтому подписка на эмберы служит лишь сигналом инвалидации.

**Последствия.** Рестарт после победы уводит на первый этаж с уже купленными
улучшениями: следующий забег короче по времени до арены, но не проще по
балансу. Dev-хуки `?floor=3`, `?boss=1` и `?embers=100` (только DEV) дают
Playwright доступ к арене и алтарю без многочасового гринд-прохождения; на UI
влияния не оказывают. Главный риск — рост урона босса в третьей фазе (×1.35)
против игрока без брони: поэтому босс появляется только после двух этажей
лута, а стартовый набор апгрейдов стоит 8–16 углей, то есть 1–3 забега.

## ADR-025. Аудио: генератор — тест, политика отдельно от Howler

**Контекст.** Звук нужен на каждой второй игровой системе (удар, крит, шаги,
дверь, сундук, костёр, голод, спуск, босс, смерть), но внешних сэмплов в
проекте нет и быть не должно: все ассеты обязаны собираться `npm run assets` в
чистом окружении. Мобильный WebAudio при этом ещё и капризен: контекст
засыпает до первого жеста, при сворачивании WebView продолжает играть, а
декодирование 18 буферов на старте легко съедает бюджет первого кадра.

**Решение.** Три уровня, каждый тестируется отдельно.

1. **Генератор = данные.** `scripts/audio/sfx.ts` держит `SOUNDS` — 18 записей
   с `id`, длительностью, пиком и функцией `build`. Рендер — чистые функции
   (`synth.ts` + `wav.ts`), поэтому тест вызывает тот же код, что и пайплайн, и
   проверяет байты: RIFF-заголовок, 22 050 Hz mono, детерминизм (два рендера
   идентичны), отсутствие клиппинга, DC ≤ 0.02, нулевой хвост, сумма ≤ 600 kB.
2. **Политика = `AudioManager`.** Группы (`sfx`/`ui`/`ambience`), громкости,
   `retriggerMs` (антипулемёт), jitter тона шагов, suspend/resume. Класс не
   знает ни про Howler, ни про DOM: бэкенд — интерфейс `AudioBackend`, поэтому
   вся логика микса покрыта unit-тестами на фейке без браузера.
3. **Плумбинг = `HowlBackend`.** Единственный модуль с `import('howler')`,
   подгружается лениво уже после того, как сцена отрисована. `loadAudio()`
   никогда не отклоняется: сломанный WebAudio в WebView не должен мешать играть.

Сцена звук не воспроизводит — у неё есть `options.onSound(id)`, как у haptic.
Движок превращает это в `audio.playSound(id)`, поэтому `DungeonScene` остаётся
тестируемым в Node без моков аудио-библиотеки и без `typeof window` в логике.

**Последствия.** Формат PCM WAV (481 kB) вместо OGG: сжатие требовало бы
внешнего энкодера, которого нет в окружении сборки, — конвертация меняется
одной строкой в `sfx.ts`, когда энкодер появится. Громкости живут в
`settings.v1` (`soundEnabled`, `sfxVolume`, `musicVolume`) и применяются только
через стор — прямых `Howler.volume` из React нет. На паузе (`visibilitychange`,
`blur`) звук глушится вместе с игрой, иначе Telegram WebView продолжает играть
в свёрнутом состоянии. Playwright проверяет только контракт (манифест v2, нет
404 на `/assets/audio/*`, микшер поднялся): headless-браузер всё равно молчит.

## ADR-026. Полировка: уровни забега, хит-стоп и пауза как отдельные системы

**Контекст.** К этапу 11 игра уже полностью рабочая, но «на ощупь» плоская:
удар не чувствуется, опыт убийств копится только в итогах забега, кнопка ☰
мгновенно выбрасывает в меню и теряет забег, а авто-деградация качества молча
делает картинку мыльной. Это четыре независимые проблемы, и каждая решается в
своём слое, а не размазыванием по сцене.

**Решение.**

1. **Уровни — правила, а не сцена.** `src/data/levels.json` + `LevelTrack`
   (чистый класс) хранят кривую `baseXp × growth^(n−1)` с потолком 12 и бонусы
   за уровень. Сцена только зовёт `grantXp()` и пересобирает статы в одной точке
   (`combinedBonuses`: мета + снаряжение + уровни). `Health.setMax` уже умеет
   добавлять разницу к текущему HP, поэтому уровень приходит «заполненным» — это
   и есть ощущение награды, без отдельного кода лечения.
2. **Хит-стоп — часы движка, а не сцены.** Сцена не управляет временем: она
   просит заморозку (`requestHitStop`, как `shake`), движок владеет `HitStop`,
   тикает его реальным `dt` и отдаёт масштаб симуляции. Отсюда два следствия,
   которые иначе легко сломать: заморозка всегда заканчивается (таймер не
   тормозится сам собой), а `PerfMonitor` и камера не видят «просадку» и не
   запускают ложное понижение пресета. Перекрывающиеся запросы берут самую
   длинную длительность и самую глубокую заморозку, а последние 30 % окна
   плавно возвращают 1× — иначе возврат читается как пропущенный кадр.
3. **Пауза — оверлей, а не выход.** ☰ замораживает забег и открывает экран с
   «Продолжить / Настройки / В меню». Выход в меню помечен как потеря забега и
   вынесен вниз, отдельной тихой кнопкой: случайный тап по ☰ не должен стоить
   двадцати минут.
4. **Деградация не молчит.** Смена пресета автоматически показывает тост —
   иначе «стало мыльно» выглядит как баг, а не как адаптация к слабому GPU.

**Последствия.** Уровни живут только внутри забега (постоянный рост остаётся за
углями и алтатарём): две оси прогрессии не конкурируют за одну награду, и смерть
не обнуляет купленное. Хит-стоп масштабирует и физику, и сцену, но не ввод:
нажатия обрабатываются мгновенно, поэтому кнопки не «залипают» во время
заморозки. Dev-хук `?xp=N` банкует опыт и даёт Playwright путь к баннеру
повышения без многочасового гринда; на прод-сборку он не влияет.

## ADR-027. Telegram: облако как зеркало, а не как источник правды

**Контекст.** Telegram WebView — враждебная среда для хранения: iOS вычищает
данные сайта «по возрасту», Android-клиент ограничивает квоту, а пользователь
может открыть мини-апп на втором устройстве. IndexedDB (Dexie) остаётся быстрой
и офлайн-дружелюбной, но потерять 200 углей из-за очистки кэша — это баг,
который игрок не прощает.

**Решение.** CloudStorage (Bot API 6.9+) используется как **зеркало записи**:

- чтения всегда идут из Dexie — приложение работает офлайн и не ждёт сеть;
- запись сначала ложится в Dexie, затем копируется в облако (`saveMirrored`);
- при загрузке, если локально **ничего нет**, значение один раз поднимается из
  облака и записывается обратно (`loadMirrored`);
- никакого слияния и фоновой синхронизации: одно устройство, один пользователь,
  а merge-алгоритм — это класс багов, которые дороже проблемы, которую решают.

Сентинел «пусто» — это `null`, а не `{}`: без него дефолтные настройки
перезаписывались бы устаревшей облачной копией при каждом запуске.

Там же, на этапе 12: имя игрока читается из launch-параметров один раз и
используется только для приветствия (никуда не сохраняется и не отправляется);
кнопка «Позвать друга» строит `t.me/<bot>?startapp=ref_<id>`, где payload
санитизируется до `[A-Za-z0-9_-]` и 64 символов; нативная кнопка «назад» теперь
привязана к каждому оверлею (пауза, настройки, титры, алтарь), иначе на iOS
единственный способ закрыть шторку — угадать, что стрелка ничего не делает.

**Последствия.** В браузере и в старом клиенте все вызовы деградируют в `null`
(шит настроек честно пишет «прогресс только на этом устройстве»), поэтому
Playwright и локальная разработка видят то же поведение, что и продакшн, без
моков хранилища. CloudStorage ограничен 128 KB на значение — снимок меты и
настроек это единицы KB, и превышение логируется, а не обрезается молча.

## ADR-028. Релиз: ассеты-иконки в коде, публикация — ручным workflow

**Контекст.** Этап 13 — это не новая механика, а два вопроса, на которых
проекты обычно и спотыкаются в самом конце: «чем приложение выглядит в списке
приложений» и «как оно попадает на устройство». И то и другое легко сделать
непроверяемым: бинарная иконка из дизайн-тула, деплой «на глазок» с локальной
машины.

**Решение.**

1. **Иконка — тоже генератор.** `scripts/icon.ts` рисует знак (каменная арка с
   угольком) в нормализованных координатах, с 2×2 суперсэмплингом, и кодирует
   настоящий RGBA-PNG через `node:zlib` — без native-зависимостей вроде sharp и
   без бинарников в git. `npm run assets` добавляет к сборке три размера
   (192 / 512 / maskable 512), а тест читает PNG обратно: сигнатура, IHDR
   (8 бит, colour type 6), длина распакованных сканлайнов, непрозрачность,
   контраст уголька и детерминизм байтов.
2. **Установка описана манифестом.** `public/manifest.webmanifest` —
   `display: fullscreen`, `orientation: landscape`, тёмный фон: ровно те
   ограничения, которые игра и так требует, теперь заявлены системе, а не только
   проверяются кодом на лету.
3. **Публикация — ручной workflow.** Pages в репозитории legacy (из ветки), а
   сборка лежит в `dist/`; переключить источник без admin-прав CI не может.
   Поэтому `.github/workflows/deploy.yml` запускается через `workflow_dispatch`
   и заново прогоняет typecheck/tests/build/size перед публикацией артефакта.
   Автодеплой на каждый push, который падал бы на настройках Pages, красил бы
   ветку и прятал настоящие ошибки CI.
4. **Сброс прогресса — параметр, а не кнопка.** `?reset=1` чистит локальные
   таблицы и облачные зеркала, спрашивает подтверждение и убирает параметр из
   URL перед перезагрузкой. Это спасает QA (первый запуск всегда доступен) и
   поддержку (испорченные данные), не добавляя разрушающую кнопку в UI.

**Последствия.** Иконки и манифест не попадают в git, как и остальные ассеты —
`npm run assets` воспроизводит их побайтово, а `npm run size` учитывает их в
общем бюджете (2.49 MB gzip из 3 MB). Деплой остаётся одной командой в GitHub
UI, с явным списком шагов в `docs/DEPLOY.md`; цена — ручной запуск вместо
пуш-в-прод, что для мини-аппа с одним окружением приемлемо.
